# Changelog

All notable changes to the EOP Server Node Registry project will be documented in this file.

## [Unreleased]

### Added

- **Edge telemetry dashboard and latency alert (US-405, #73):** the Grafana dashboard **EOP Edge Telemetry** (`eop-edge`) shows the ingestor's broker connection, E2E latency P50/P99 (device sampling → eop-server ACK) against the 500 ms NFR, messages per second (received, forwarded, duplicates, invalid), the message loss rate from device buffer overflows, and a per-device table (connected / disconnected, last seen, dropped, buffered, thread restarts) from the new `eop_edge_device_last_seen_timestamp_seconds`. The alert `eop-edge-e2e-p99` fires when P99 stays above 500 ms for more than 1 minute; dashboard and alert are provisioned in docker-compose and Kubernetes and checked by `make edge-dashboard-test` (also: every queried metric is one the ingestor exports). The `edge.message` span now carries `edge.sampled_at`, `edge.received_at`, `edge.delivered_at` and `edge.e2e_latency_ms`. `make edge-test` runs 5 minutes of edge-sim against docker-compose and checks, from Prometheus with the dashboard's own expressions, that every published message was forwarded, the panel rate matches the real one, P99 < 500 ms and nothing was lost.
- **Edge telemetry reaches eop-server (US-404, #72, ADR-028):** eop-server accepts `TELEMETRY node_id=… bunker_name=… message_id=… boot_id=… temperature=… status=… sampled_at=… [traceparent=…]` (validated key by key, `ERROR_INVALID_REQUEST desc=<reason>` otherwise) and keeps each device as an edge node (`source=edge`, in memory or in the shared Redis registry), ONLINE while its last telemetry is younger than `EOP_EDGE_LIVENESS_TIMEOUT` (10 s); the newest sample by `sampled_at` is the one shown, so a flushed buffer does not hide newer data, and a `node_id` registered over TCP answers `ERROR_DUPLICATE`. `LIST_NODES`/`QUERY_NODE` append `source=edge temperature=… device_status=… sampled_at=…` to edge nodes only; v0.1 lines are unchanged. The Go **edge-ingestor** subscribes to `eop/bunker/+/telemetry` with QoS 1 and a persistent session, acknowledges a message to the broker only after the server's ACK, deduplicates by `(node_id, boot_id, message_id)` in Redis for 5 minutes, retries a down server with logged backoff, reconnects to the broker, traces each message (`edge.message` → `edge.ingest` → server) and exports `eop_edge_*` metrics including the end-to-end latency per device. **edge-sim** publishes the firmware's payload for N devices. The gateway adds `GET /v1/edge/status` and a `telemetry` object on edge nodes in `/v1/nodes`. Mosquitto (persistent sessions, TLS device listener with locally generated certificates) and the ingestor run in docker-compose and Kubernetes. `make edge-integration-test` (US-404 AC8): 10 simulated messages reach `/v1/nodes`, and none is lost while the server is down.
- **Shared node registry and eop-server failover (US-407 AC4, #71, ADR-027):** the registry is behind `INodeRegistry` (`include/nodeRegistry.hpp`) with the v0.1 in-memory backend (default) and a Redis backend (`include/redisNodeRegistry.hpp`, hiredis via vcpkg, RAII) selected by `EOP_REGISTRY_BACKEND=memory|redis`. In Redis each node is a hash with its owner replica, each replica holds a 3 s lease, and a node is ONLINE only while its owner's lease lives: the nodes of a dead replica read OFFLINE everywhere within 3 s and re-register on the other one; `REGISTER` is one Lua script, so `ERROR_DUPLICATE` holds across replicas. A replica rewrites its live nodes after Redis loses them, answers `ERROR_SERVICE_UNAVAILABLE desc=Node registry unavailable` when Redis is down, and its readiness port (`EOP_READY_PORT`) is open only while the registry answers and it is not shutting down; on SIGTERM it keeps serving for `EOP_SHUTDOWN_DRAIN_MS` after leaving the Service. In Kubernetes eop-server runs 2 replicas with a PodDisruptionBudget, and hpc-engine moves into its Pod as a sidecar registered as `hpc-engine-<pod>` (the `hpc-engine` Deployment is removed; a Prometheus job scrapes the sidecar). `mttr-watcher` (Go, `services/go/cmd/mttr-watcher`) measures service restoration and replica replacement from Pod and EndpointSlice events and exports `eop_mttr_*` for a new MTTR row in the SLO dashboard; `make k8s-mttr-test` deletes a Pod under a 20 ms probe and fails at 200 ms. Measured on minikube: 0 of 1,955 probe requests failed, service restoration 93 ms, replica replacement 3.4 s.

### Fixed

- **A command left without `\n` when a client closed could be answered to another client (#71):** the server queued it and closed the socket at once, so a new connection could get the same fd before the worker wrote the answer. The session now stays open, out of the poll set, until the worker has answered, which also makes a half-closed client (`printf 'LIST_NODES' | nc`) get its answer.

## [0.3.0] - date set when release/0.3.0 is cut

Public API & Safe Delivery (Milestone 3): a versioned REST API in front of the EOP server, canary and blue-green delivery of that API, and logs centralized in Loki and correlated with traces.

### Added
- **REST API P99 measured from the client (v0.3 NFR, ADR-010 §6, #57):** `tests/load/gateway_load.py` reports P50/P95/P99 per path and `--max-p99 MS` fails the run over the limit; `make gateway-p99-test` runs it for 60 s through the Ingress with a 300 ms limit. On minikube, 8 clients on `/v1/health`, `/v1/nodes` and `/v1/openapi.json` (8,487 requests, no errors) gave P99 of 58.3, 48.5 and 43.8 ms; the gateway's own histogram in Prometheus gave 36.9 ms over the same 5 minutes.
- **Blue-green delivery of the API gateway (US-305, #56):** `k8s/api-gateway/overlays/blue-green` (ADR-011 §3) runs two complete Deployments, `api-gateway-blue` and `api-gateway-green`, behind `api-gateway-active`, whose selector names the live slot; each slot also has its own preview Service. `make blue-green-deploy IMAGE=… VERSION=…` starts the new version in the idle slot, `make blue-green-switch` runs the smoke suite `tests/smoke/gateway_smoke.py` (health, node listing and a sample graph analysis, every response required to come from the new version) against that slot's preview Service and, only if it passes, moves the selector with one patch; `make blue-green-rollback` moves it back the same way. Both report, from the client side, how long clients kept reaching the slot being left. `make blue-green-layout` / `make canary-layout` move the gateway between the two layouts carrying the serving version over, and `make gateway-smoke-test URL=…` runs the suite against any gateway. Rehearsed on minikube under continuous load: a green slot with a broken analysis was stopped by the smoke tests and blue stayed active; switch, rollback and switch again took 4.1–4.6 s (limit 10 s) with 17,272 requests and no client error. CI checks the rendered blue-green layout (disjoint slots, no Service selecting both, active on blue, Ingress on the active Service) and that the smoke suite rejects each kind of broken slot. `tests/k8s/log-trace-correlation.py` reaches the gateway in either layout.
- **Canary release of the API gateway (US-304, #55):** `k8s/api-gateway/overlays/canary` (ADR-011) runs `api-gateway-stable` and `api-gateway-canary` from one base Deployment, each with the track in its selector; the shared Service `api-gateway` selects both, two per-track Services give ingress-nginx distinct backends, and the Ingress host `api.eop.local` sends `canary-weight` percent of the requests to the canary (versioned at 0, with the canary at 0 replicas). `make canary-deploy IMAGE=… VERSION=…`, `canary-rollout WEIGHT=N` (refuses a weight above 0 while the canary has no ready pod), `canary-rollback`, `canary-promote` and `canary-status` (`scripts/canary.sh`) change only the weight annotation during a rollout; `make k8s-apply` now deploys this layout. Gateway responses carry `X-EOP-Version` and `X-EOP-Track` from the pod labels, which `make gateway-load-test` (`tests/load/gateway_load.py`) uses to report the live split per version and to fail on any 5xx or connection error. The SLO dashboard gains error rate, P99 and requests per second per version and track, and a Grafana alert fires when the canary's 5xx share exceeds 1 % over 5 minutes, the rollback trigger documented in `docs/RUNBOOK.md`. Rehearsed on minikube under continuous load: 10 % → 50 % → 100 %, rollback, 10 % and promote with 24,068 requests and no client error; rollback measured at about 1.1 s from 50 % and from 100 % (limit 30 s). Static tests in CI check the rendered overlay (disjoint selectors, shared Service, Ingress backends, weight 0, safe rollout settings) and the load tool.
- **Centralized logging in Loki with trace correlation (US-306, #54):** Loki (single binary, `k8s/loki/`, PersistentVolumeClaim) keeps 7 days of logs, with retention as code in `monitoring/loki/config.yaml` enforced by the compactor; an `otel-log-agent` DaemonSet (OpenTelemetry Collector, `monitoring/otel-log-agent/config.yaml`; Promtail reached end of life) reads every pod's log files, turns the JSON fields of EOP logs into structured metadata, uses `trace_id`/`span_id` as the record's trace context and `level` as its severity, checkpoints its offsets on the node and ships to Loki over OTLP. Grafana gets a Loki datasource whose `trace_id` links to the trace in SigNoz and an *EOP Request Logs* dashboard filtered by service, level and `trace_id`. `eop-server` logs now carry `service` (ADR-019) and accept the optional `traceparent=` key on text commands (ADR-026): its spans continue the caller's trace, so a request through the API gateway is one trace across both services, and each failed traced operation writes an ERROR line inside its span. `docs/RUNBOOK.md` starts with "From a Grafana alert to the request logs". Tests: W3C traceparent parser unit tests, a smoke test against the real server with a fake OTLP collector, a static Loki contract test in CI (`make loki-test`), and `make k8s-log-trace-test`, which checks on a running cluster that a failed request has the same `trace_id` in SigNoz and Loki — passed on minikube, as did collecting lines written while the agent restarted and keeping lines across a Loki restart.
- **Circuit breaker for external services (US-303, #53):** `GET /v1/nodes/{node_id}/insights` (AI service) and `GET /v1/nodes/{node_id}/corporate` (corporate service, by the node's bunker) go through one circuit breaker per service (`internal/breaker`, ADR-012): it opens after 5 consecutive failures or more than 50 % errors in a sliding 10 s window with at least 10 calls, probes again after 30 s with one call, and its thresholds and call timeout live in the `api-gateway-breaker` ConfigMap, re-read every 10 s without resetting the circuits (verified on minikube: applied 26 s after editing the ConfigMap, no restart). While a service fails or is open, the gateway serves the last good answer marked `meta.stale`/`stale_since`, or `503 SERVICE_DEGRADED` with `Retry-After` — never `500`; both fallbacks are in the OpenAPI contract. State, transitions and fallbacks are exported as `eop_gateway_circuit_state`, `eop_circuit_breaker_state_transitions_total` and `eop_gateway_fallback_responses_total`, charted in two new SLO dashboard panels (dashboard contract test extended), and every transition is a span event and a log line. The external services are represented by `external-stub` (one binary, two Deployments in `k8s/external-stubs/`, two compose services, own image target) with runtime fault injection. An integration test stops the AI stub, sees the circuit open and the fallback served, restarts it, sees the circuit close, and checks that a settings change applies live. The compose Prometheus now scrapes the gateway.
- **Graph analysis REST API with asynchronous jobs (US-302, #52):** `POST /v1/graph/analyze` answers graphs under 1,000 nodes synchronously (5 s budget, `504` beyond it) and turns larger ones into jobs (`202` + `job_id` + `Location`); `GET /v1/graph/jobs/{job_id}` returns state and result, `GET /v1/graph/jobs` the recent jobs without results. Jobs live in Redis (`k8s/redis/`, compose service) with a 5-minute TTL after they finish, so a poll is answered by any gateway replica — verified on minikube with two replicas, posting to one pod and polling the other. Requests are validated in the gateway before they reach the engine (`400` naming the offending field), engine errors are mapped without exposing internals, and an offline engine gives `503 HPC_UNAVAILABLE` (checked before accepting a large job, using the ADR-022 `hpc-engine` node naming). Jobs run on a bounded per-pod worker pool (`429` with `Retry-After` when full); on SIGTERM the gateway drains HTTP first, then lets jobs finish within the shutdown budget and records the rest as `GATEWAY_SHUTDOWN`. `/v1/health` reports `degraded` when Redis is down instead of leaving the Service. Integration tests run the full gateway against the real `eop_server` and `hpc_engine` (sync, 1,200-node async flow, job list, invalid graph, engine offline).
- **API gateway in Go with the node state REST API (US-301, #51):** `services/go/` holds a Go module (ADR-010) with `GET /v1/nodes`, `GET /v1/nodes/{node_id}`, `GET /v1/health` (readiness) and `GET /v1/openapi.json`. Responses use the `{data, meta}` envelope and structured errors; eop-server failures map to `503`/`502` without exposing internal details, and `node_id` is validated before it reaches the socket protocol, so a path such as `/v1/nodes/a%0ALIST_NODES` cannot inject a second command. The gateway talks to eop-server through `internal/eopclient`, a pooled TCP client that evicts connections before the server's idle timeout, retries read-only commands once on a stale connection, bounds response size, and appends the optional `traceparent=` key (ADR-026) — verified against the real `eop_server`, which ignores it. The OpenAPI 3.0 contract is hand-written in `services/go/api/openapi.yaml`; unit tests validate every response against it and fail if a route is served but not documented, or documented but not served. Metrics (`eop_gateway_http_requests_total`, `eop_gateway_http_request_duration_seconds`, labeled by route pattern, version and track) and `/livez` are on a separate internal port. Distroless image of 19 MB, Kubernetes base in `k8s/api-gateway/base` (readiness on `/v1/health`, liveness on `/livez`, native `preStop` sleep, read-only root filesystem), `docker-compose.yml` service, `make gateway-*` targets, and a `go-gateway` CI job (gofmt, golangci-lint, vet, race detector, coverage ≥ 90 %) plus the AC8 integration tests against the `eop_server` built in the main job.
- **v0.3 architecture decisions (#50):** `ADR-010` API gateway in Go (REST contract under `/v1`, gateway SLOs (P99 < 300 ms, 5xx error rate), hand-written OpenAPI, shared EOP protocol client for the v1.0 edge-ingestor, async analysis jobs in Redis so any gateway replica can answer a poll), `ADR-011` canary and blue-green delivery on ingress-nginx (including how US-304 AC7's "same Service" is met when nginx needs one backend per track), `ADR-012` circuit breaker per external service with a sliding window and hot-reloaded ConfigMap, plus one configurable stub standing in for the AI and corporate services, and `ADR-026` centralized logging in Loki through an OTel Collector DaemonSet (Promtail reached end of life on 2026-03-02), with an optional, backwards-compatible `traceparent=` key on text commands recorded as an `ADR-003` addendum.

### Changed
- **`ANALYZE_GRAPH` forwards the server's span to the engine even when the caller sent a `traceparent` (#54):** the server's span now continues the caller's trace, so the engine hangs from the span that dispatched it; the trace-id is unchanged.
- **ADRs follow the PRD numbering and live in `docs/adr/` (#50):** ADR-001 to ADR-014 now match the PRD reference index, and the squad's additional decisions are numbered from ADR-015 in the order they were taken. `docs/adr/README.md` is the index and maps every previous number to its current one; references in code comments, tests, configuration, documentation and this changelog were updated.

### Fixed
- **API gateway connection pool could reuse a desynchronized connection (#52):** a connection went back to the pool after any `ERROR_*` answer, so if the server ever sent an extra line — as servers built before the #55 framing fix do for long requests — the next command on that connection read the stale line (seen on minikube as the readiness probe failing with `Unknown command`). Only the expected `ERROR_NOT_FOUND` keeps a connection; `ANALYZE_GRAPH` never reuses one. Cancelling a request now also interrupts a blocked read.

## v0.2 close-out - 2026-09-09

Brought over from `ICOMP-UNC/sd-2026-af-developers`, where v0.2 is tracked and released; issue numbers in this section refer to that repository.

### Added
- **`hpc-engine/benchmarks/BENCHMARK_REPORT.md` regenerated from a real `make benchmark` run** (Release build, plugged in, cooled between runs, the actual command US-202 AC7 names -- not the `HPC_ENGINE_BIN`-with-an-external-binary workaround used earlier while the link was broken, see the Fixed entry above). Raw measurements saved alongside it as `BENCHMARK_REPORT.json`. This is the data backing the `EOP_HPC_BASELINE_*` values below and `docs/release-0.2.0-known-limitations.md`.
- **`EOP_HPC_BASELINE_P99_MS`/`_GRAPH_NODES`/`_BAND_PERCENT` configured with real measured data** (US-206 AC1/AC4, ADR-023): 6744 ms / 10000 / 20, from the Benchmark Report's 10,000-node single-thread row (worst of 3 runs, as a conservative P99 substitute). `eop_hpc_speedup_ratio` and `eop_hpc_baseline_seconds` now publish on `/metrics` for in-band requests; verified end to end against a live `eop-server`+`hpc-engine` pair. These three keys were previously commented-out placeholders pending a benchmark run -- the run itself is what §1's `BENCHMARK_REPORT.md` entry restores.
- **`docs/release-0.2.0-known-limitations.md`**: the three US-202/NFR items measured and found not to pass at v0.2 close-out (AC2 at 100,000 nodes, AC3 without 8-physical-core hardware, pod-crash MTTR), each with root cause, evidence and what would resolve it -- written for the course staff, not hidden.
- **The original US-102 workloads can be run and were demonstrated (ADR-020):** CI keeps the reduced load test, and `EOP_LOAD_CLIENTS` / `EOP_LOAD_REQUESTS_PER_CLIENT` restore the figures the PRD asks for. The test now also reports P50/P95/P99 latency, fails on `ERROR` replies (AC8 asks for zero server-side errors, and any reply used to count as success), and can pace clients at a fixed rate (`EOP_LOAD_REQUEST_INTERVAL_MS`) for AC2's same-workload comparison. `tests/evidence/` adds a 1M-cycle descriptor-leak test (AC4), an end-to-end US-201 AC3 measurement, and a watchdog that stops a run before the machine runs out of memory or overheats. Results are in ADR-020. Along the way: the server accepts one connection per `poll()` wakeup, so a connection burst overflows the listen queue and each dropped SYN costs the client a 1 s retry.
- **Prometheus + Grafana observability stack (#43):** deployed in both targets — `docker-compose.yml` for local work and `k8s/` for the cluster — with the SLO and HPC dashboards provisioned from `monitoring/grafana/dashboards/`, which stays the single source of truth for panel content (the K8s ConfigMap is generated from that directory by `make k8s-apply`, not committed as duplicated YAML).
- **Grafana native alerting (US-205 AC3, US-206 AC4):** two provisioned rules under `monitoring/grafana/provisioning/alerting/`. `eop-error-budget-below-50` fires when the monthly error budget drops under 50% for 5 minutes, matching `ADR-009`'s policy (>50% normal, 10-50% caution, <10% freeze); `eop-hpc-p99-above-2x-baseline` fires when the engine's P99 exceeds twice its configured single-thread baseline for 2 minutes. Chosen over Prometheus + Alertmanager because it reuses the existing provisioning structure, adds no new component to a memory-constrained cluster, and satisfies the AC's "visible in the server logs" half for free — Grafana logs every rule state transition itself.
- **Full SigNoz stack on Kubernetes (US-203 AC5, US-206 AC5):** ClickHouse, ZooKeeper, the schema-migrator Job, SigNoz, its internal collector, and the generic `otel-collector` that `eop-server` exports to, plus `OTEL_EXPORTER_OTLP_ENDPOINT` in the global ConfigMap. Previously the whole stack existed only in docker-compose, so in-cluster `eop-server` fell back to its `localhost:4318` default and **every span was silently dropped**.
- **Graph size limits (`ERROR_GRAPH_TOO_LARGE`, #51):** the error code and `EOP_MAX_GRAPH_NODES` / `EOP_MAX_GRAPH_EDGES` were documented in the protocol but had no implementation — there was no size validation at all. Added in `hpc-engine/src/validator.cpp`, plus a third, much stricter limit that was not in the original scope: `EOP_MAX_SHORTEST_PATHS_NODES` (default 300), applied only when `shortest_paths` is requested. That algorithm returns the full path for every reachable pair, so total path-node entries are O(N³): on a 1000-node graph the process passed 6GB RSS and climbing, and **froze the development machine**. It is reproducible with a real `ANALYZE_GRAPH`, not a test artifact.
- **Single-thread baseline for the speedup ratio (US-206 AC1/AC4):** `ComputeConfiguredSpeedupRatio` in `hpc-engine/src/metrics.cpp`, driven by `EOP_HPC_BASELINE_P99_MS` / `_GRAPH_NODES` / `_BAND_PERCENT`. A scalar baseline is only comparable between graphs of similar size, so the ratio is published **only** when the request's graph falls inside a documented tolerance band, and nothing is published outside it. See `docs/adr/ADR-023-hpc-speedup-baseline.md`. The three keys are deliberately left commented out in `k8s/configmap.yaml` until the OpenMP Benchmark Report produces a real measurement — a placeholder there would be exactly the unfounded magic number the SW-Agreement prohibits.
- **v0.1 protocol backward-compatibility contract test (US-203 AC8):** `tests/smoke/v01_protocol_backward_compat.py` replays the full v0.1 message corpus against a real `eop_server` and asserts each response keeps its documented shape. The AC mentions `buf breaking`, which does not apply — `buf` is a protobuf tool and this protocol is newline-delimited JSON (`ADR-003`).
- **Contract tests for the Prometheus scrape config and both dashboards**, wired into CI (they are static and need no running Grafana).
- **Per-request engine logging (US-201 AC5):** the engine emitted no per-request log line at all. It now writes one structured JSON object per request to stderr with the graph size received, the algorithms executed, the wall-clock processing time and the thread count, plus the `timestamp`/`level`/`service`/`trace_id` fields the observability NFR requires. stderr rather than stdout because stdout carries protocol responses in batch mode.
- **Thread utilization metric and panel (US-206 AC6):** `eop_hpc_thread_count` reports how many threads were *configured*, which the AC does not ask for. Added `hpc::ActiveThreadScope`, constructed once per worker per parallel region in `centrality.cpp`, `dijkstra.cpp` and `connected_components.cpp`, publishing `eop_hpc_active_threads` (instantaneous) and `eop_hpc_thread_busy_seconds_total` (accumulated thread-seconds). Both are needed: a request that begins and ends between two Prometheus scrapes is invisible to the gauge, so a busy engine would chart as flat zero; the counter's rate cannot miss that work. Serial stretches of a request -- parsing, validation, serialization -- are deliberately outside the scope, so the panel does not claim utilization the engine is not achieving. Charted in the new "OpenMP Thread Utilization" panel against the configured ceiling.
- **End-to-end trace context propagation (US-203 AC5, US-206 AC5):** the `traceparent` field was documented in the protocol and read by the engine, but **both halves of the chain were missing**. `eop-server` never wrote a `traceparent` into the request it dispatched (a grep for writers returned nothing), and `hpc-engine` never initialised a `TracerProvider`, so it emitted no spans of its own. The result was that a trace stopped at the server: every span in SigNoz belonged to `eop-server`, and the engine's work — the part actually worth measuring — was invisible. Added `buildTraceparentFromCurrentSpan()`/`injectTraceparent()` on the server side and `hpc/tracing.hpp` on the engine side, which parses the incoming `traceparent` into a remote `SpanContext` and emits `hpc.analyze_graph` plus one child span per algorithm. A malformed or absent `traceparent` falls back to starting a new trace rather than dropping the work. Covered by a smoke test asserting that the trace-id the engine receives is the one the server logged.

### Changed
- **Prometheus service discovery unified (US-205 AC4):** `eop-server` used a static scrape target while `hpc-engine` was discovered by pod annotation. Both now carry `prometheus.io/scrape|path|port` and are covered by a single `annotated-pods` job using `kubernetes_sd_configs`, which is what the AC asks for.
- **SLO panels are gauges with explicit thresholds (US-205 AC2):** "Service Availability" and "Error Budget Remaining" were plain `stat` panels with an empty threshold array. Now gauges with red/yellow/green steps aligned to `ADR-009`'s error budget policy.
- **Grafana access documentation moved to `README.md` (US-205 AC8):** the AC names the README specifically; the per-dashboard docs keep only their own troubleshooting.
- **The HPC panel documentation now references the OpenMP Benchmark Report (US-206 AC3)** as the historical evidence for reading it, with a panel-by-panel table of what to compare against: the report's per-thread timings, its measured speedup, its Amdahl serial fraction (which sets the achievable utilization ceiling), and its "when not to parallelize" minimum graph size. The link is more than documentary -- the baseline behind the speedup panel and the P99 alert is a number that report measures.
- **`make k8s-apply` waits up to 3 minutes per rollout** instead of 60s, which US-204 AC6 requires and which had already failed live — Grafana's 1.4GB image alone took ~70s to pull on a cold node.
- **Betweenness centrality is estimated by source sampling above a configurable graph size (ADR-024):** exact Brandes is O(V·E), and in the US-202 benchmark it took ~18.5 minutes per request at 100K nodes with 4 threads. Two changes: memory layout (CSR adjacency, predecessors in one intrusive buffer, resetting only the nodes each source touched), 1.4x faster at 10K nodes with the same values up to floating-point rounding and an identical ranking; and, above `EOP_HPC_CENTRALITY_EXACT_MAX_NODES` (default 2000), scores estimated from `EOP_HPC_CENTRALITY_SAMPLES` (default 1024) sampled sources rescaled by V/k (Brandes & Pich), with a fixed seed. 4.9 s at 100K nodes. The approximation is declared in `result.algorithm_metadata.centrality` and the values are for ranking, not for quoting. ⚠️ Pending the course staff's agreement. Measured plugged in, exact already meets US-201 AC3 at 10K nodes (3.42 s end to end), so `ADR-024` recommends raising the threshold to 10,000: exact where the AC applies, sampled only beyond it. Earlier versions of this entry quoted 39.6 s and 7.9 s: the first came from an `-O0` build and the second from a run on battery.
- **`ADR-024` option D applied: `EOP_HPC_CENTRALITY_EXACT_MAX_NODES` default raised from 2,000 to 10,000.** US-201 AC3 names a 10,000-node graph, and exact centrality already meets its 5 s budget at that size (3.42 s end to end, plugged in) — so the AC is now satisfied without approximating anything, and pivot sampling only ever applies to graphs larger than any AC's latency figure names. `k8s/configmap.yaml` sets the same value explicitly (rather than relying on the code default) so the deployed behaviour is visible without reading source. Also brought `OMP_NUM_THREADS` in the K8s ConfigMap from 1 to 4 to match what US-201 AC3 actually measures — it had never been raised past the single-thread value used before the engine supported concurrency — and `hpc-engine-deployment.yaml`'s CPU/memory limits with it: `limits.cpu` 1 → 4 (OpenMP throttles under the cgroup quota below its thread count regardless of `OMP_NUM_THREADS`), `limits.memory` 256Mi → 512Mi, sized from measured peak RSS rather than guessed (a 100,000-node pivot-sampled request peaked at ~309 MiB at 8 threads, ~287 MiB at the 4 the Deployment runs with).

### Fixed
- **`run_benchmark.sh` (and therefore `make benchmark`) did not link on a non-Alpine host:** it forced `-DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++` for this project's own build, but vcpkg builds its own ports (civetweb, statically linked into `prometheus-cpp-pull`) with the ambient default compiler for the triplet, not whatever this project's CMake invocation asks for. On this triplet civetweb's `Release` variant is compiled with `-flto` using the system `c++` (GCC on a typical glibc host), and GCC's LTO bitcode is a different format from LLVM's -- neither GNU `ld` without GCC's own LTO plugin nor `clang`/`lld` can read it, so the *link* failed with dozens of `undefined reference to CivetHandler::...` errors, not the compile. `hpc-engine/Dockerfile` (which CI already validates) never hit this because its Alpine builder's default compiler is GCC throughout, matching what vcpkg used for its own ports. Fixed by no longer overriding the compiler and letting CMake pick the ambient default, same as the Dockerfile. Confirmed end to end: a full `make benchmark` run now completes in ~13 minutes and regenerates `BENCHMARK_REPORT.md` and `BENCHMARK_REPORT.json` from a real `Release` build (US-202 AC7). Along the way, the report's own "Compilador" field was wrong: it always shelled out to `clang++ --version` regardless of which compiler actually built the binary being benchmarked -- so once the link fix stopped forcing clang, the report would have kept claiming the engine was built with clang while it was actually GCC. Fixed to read `CMAKE_CXX_COMPILER` back out of the configure step's own `CMakeCache.txt` and version that binary, so the field always names the compiler that produced the binary being measured, not a fixed guess.
- **`run_benchmark.sh` measured the wrong thing:** `AC2A_SIZE` was 5000 and `SIZES` topped out below the PRD's requirement, so the benchmark could pass without ever testing the acceptance criteria (≥50K nodes for AC2, and the 10K/50K/100K set for AC5). Also separated the "physical CPUs" label, which reported `nproc` — logical threads, not physical cores.
- **The Benchmark Report drew conclusions its own data did not support (#51):** the first run on a second machine (i7-10510U, 2026-09-17) exposed four problems in how `run_benchmark.sh` analysed its measurements. *Amdahl was fitted on hyperthreads*: it derived the serial fraction from the 8-thread run, which on a 4-core machine is two threads per core sharing cache and memory bandwidth, and reported **s = 0.76** — refitted on 2 and 4 threads the same data gives 0.49 at 100K and 0.13 at 10K, and even those high values at 50K/100K reflect a memory ceiling rather than serial code. *The conclusion was a fixed paragraph* claiming "significant gains from 5,000 nodes" in a run that measured 0.90× at 50K, and naming a "< 1,000 nodes" threshold that nothing below 10K had measured. *The small sizes were missing*, which was my own regression: correcting the sizes to the 10K/50K/100K that AC5 names removed the only data AC6 ("when not to parallelize") can be derived from. *Nothing distinguished physical cores from hyperthreads*, so an 8-thread criterion that cannot be measured on 4 cores was reported as a plain failure. The measurement, analysis and report now live in `benchmark_report.py`: Amdahl is fitted by least squares on thread counts within the physical cores only, a size that gains on real cores but gets *clearly* slower with extra hyperthreads (ranges not overlapping, so millisecond-scale noise does not count) is named as a memory ceiling, which Amdahl cannot produce, while sizes that never gain are reported as n/a instead of as "fully serial"; AC6 is computed from sizes starting at 10 nodes (on a 4-core laptop, below 100–200 nodes starting a team of threads costs more than the work itself — 0.29× at 10 nodes); every conclusion is derived from the tables; AC3 is reported as *not measurable* rather than failed when there are fewer than 8 physical cores; AC8 is measured (process CPU time over wall time, against `OMP_NUM_THREADS`) instead of left to watching `top`; each measurement is the median of 3 runs with its range; every size requests the same two algorithms, where the generator used to add `shortest_paths` below 500 nodes and would now hit its 300-node limit; and the graph is generated from a fixed seed (`generate_graph.py --seed`), so two machines measure the same graph. The report also records the commit, CPU model, physical cores and whether centrality ran exact or sampled. `run_benchmark.sh` drops from 369 to 107 lines and accepts `HPC_ENGINE_BIN`/`BENCH_*` to test it without a multi-hour run. A failed measurement is recorded in its row and the run continues, and the report is rewritten after every size, so an error or an interruption hours into a run no longer discards what was already measured. Running it for real added four more things. A measurement longer than a time budget is not repeated, so the full matrix fits in about 1.5 hours instead of more than a day. The raw measurements are saved next to the report as JSON, and `--rerender` rebuilds the report from them without re-measuring. `--cooldown-below` waits for the CPU to cool before each run. The power state (plugged in, profile, turbo) is recorded, because the same binary on the same graph measured 2.5–3x slower on battery. The analysis is covered by 32 tests, including the 2026-09-17 run as a regression case, and runs in CI as `make benchmark-report-test`.
- **`make tsan` invoked a script that does not exist** (`run_ci_local.sh`), so the target had never worked despite `run_benchmark.sh` citing it as the mechanism that proves US-202 AC4. Rewritten to replicate CI's `thread-sanitizer` job commands directly.
- **Invalid PromQL in the "Error Budget Remaining" panel.**
- **Five Kubernetes bugs found by running the SigNoz stack against a live minikube cluster**, none of which docker-compose exposes and none of which static validation catches:
  - *ClickHouse's Service had to be headless.* `cluster.xml` names `clickhouse:9000` as the single replica, and ClickHouse decides whether a distributed DDL task is local by resolving that hostname against its own interfaces. A normal Service's virtual ClusterIP never matches a pod IP, so `system.clusters` reported `is_local=0` and every DDL hung for the full 180s `distributed_ddl_task_timeout`.
  - *ZooKeeper needed a `startupProbe`.* The JVM's cold start outlasted the liveness grace period, so the pod was killed mid-boot and crash-looped without ever reaching Ready.
  - *ZK session timeouts were too tight for in-cluster latency*: raised to 60s on the client side (`cluster.xml`) and on the server-side cap (`ZOO_MAX_SESSION_TIMEOUT`), which silently clamps whatever the client negotiates.
  - *CPU limits caused real throttling*: `cgroup cpu.stat` showed ~40% of periods throttled on `zookeeper-1`.
  - *256Mi got the ZooKeeper JVM OOMKilled every few minutes*, and each restart orphaned whatever DDL task was queued in that window — the root cause behind hours of `Inactive` queue entries that never executed. With all five fixed the migration Job completes in **2m07s with zero restarts** (44 replicated tables, 0 readonly), against hours of failed retries before.
- **Grafana crash-loop and OOMKill in Kubernetes:** the readiness/liveness probes killed Grafana mid-migration on cold start (it runs 700+ DB migrations before answering), and its 256Mi limit was exceeded under real interactive use. Added a `startupProbe` and raised the limit to 512Mi.
- **Grafana's provisioning bind mounts in docker-compose:** mounting the whole `provisioning/` tree read-only and then mounting `dashboards/` into a subdirectory of it fails — Docker cannot create the mountpoint inside an already-read-only bind mount. Switched to individual per-file mounts.
- **`up{job=~"$service"}` silently returned nothing after unifying the scrape job:** every pod ended up labelled `job="annotated-pods"`, breaking the SLO dashboard's service selector with no error. Added a `relabel_configs` rule that rewrites `job` from the pod's own `app` label.
- **`eop-server` truncated HPC Engine responses at 64 KB:** `receiveHpcEngineResponse` read the engine's reply with a single `recv()` and treated it as complete. Centrality for a 10K-node graph is ~1 MB, so the client got 65,535 bytes of broken JSON, and the rest stayed in the engine socket to be delivered as the reply to the *next* request. Same bug class as #55, in the engine → server direction; the smoke tests used 2-node graphs and never produced a response larger than one read. Found by the end-to-end US-201 AC3 measurement. The server now peeks and consumes only up to the terminator, with the dispatch timeout as a total deadline and a 64 MB cap, and sends the reply to the client with `sendAllToSocket`. Regression test `smoke_analyze_graph_large_response` fails without the fix.
- **`eop-server` dispatched partial reads as if they were complete commands (#55):** the read loop had no per-connection buffer. When a message spanned two `recv()` calls, the first fragment was dispatched immediately as a command and the second arrived later as separate garbage — with no way for the server to know the first piece was only a prefix. This is **not** a network-only problem: it reproduces 100% of the time on localhost with any `ANALYZE_GRAPH` over 256 bytes, and it violates the newline-delimited framing that `ADR-003` defines. Short commands such as `HEARTBEAT` appeared to work purely because they always fit in a single `recv()`. Replaced with a persistent `pendingInput` buffer per session that dispatches only on a real `\n`, flushes any remainder at EOF, and drops the buffer with `ERROR_BAD_REQUEST desc=Message too long` past `EOP_MAX_REQUEST_BYTES` (64 MiB) so a client cannot exhaust server memory by never sending a terminator. That cap was first set to 8 MiB on the assumption that it left room for any request the engine accepts; it does not — a valid 100,000-node graph is 13 MiB, and at the engine's own limits a request reaches 25-30 MiB — so it would have rejected valid work before the terminator arrived. The socket read buffer also stopped being `MESSAGE_BUFFER_SIZE` (256 bytes, the size of an audit-log entry, unrelated to the network): ingesting a 13 MiB request took ~54,000 event-loop iterations and **31.5 s**, against 0.28 s with a 64 KiB buffer. Regression test covers four split patterns.
- **`libeop` never terminated its messages and swallowed the welcome banner:** `eop_send_command()` did not append the protocol's `\n` for any command type — it worked only because it leaned on the same fragile behaviour as the bug above, not because the protocol tolerates its absence. Separately, `eop_connect()` left the `WELCOME` banner unread, so the first `eop_send_command()` after connecting returned the banner instead of its own response — affecting every caller, including `examples/connect_basic.c`, which had evidently never been run against a real server. The banner is now consumed with `MSG_PEEK`, reading only up to the newline so any non-banner data that follows is left untouched for the caller.

## [0.2.0-dev] - 2026-08-08

### Added
- **HPC Engine persistent daemon mode:** `hpc-engine` now supports a socket-connected mode — triggered by passing `--server-host`/`--server-port`/`--node-id` — that registers with the EOP server as a peer and keeps servicing `ANALYZE_GRAPH` requests indefinitely, with bounded connect/register retry-backoff and a heartbeat file for external liveness checks. Without those flags it falls back to its original one-shot batch mode (stdin/stdout), so both `hpc-engine` (#13/#14) tests and callers are unaffected.
- **HPC Engine Docker image:** dedicated multi-stage `hpc-engine/Dockerfile`; the runtime stage installs `libgomp` (OpenMP runtime) and has no `EXPOSE`, since the engine is an outbound-only TCP client — it never binds or listens.
- **Kubernetes Deployment for `hpc-engine`** (`k8s/hpc-engine-deployment.yaml`): persistent Deployment with a liveness probe (process-alive check), a readiness probe (heartbeat-file freshness), CPU/memory requests and limits, and the shared `eop-global-config` ConfigMap.
- **Kubernetes batch Job demo** (`k8s/jobs/hpc-engine-batch-job.yaml` + sample-graph ConfigMap): one-shot `ANALYZE_GRAPH` run via a `Job`, exercising the batch execution path alongside the persistent Deployment — the Dual-Execution Vector described in `docs/adr/ADR-017-kubernetes-workload-management.md`.
- **CI:** the Docker image build matrix now covers both `eop-server` and `hpc-engine`, each validated against the 50MB runtime image size limit; a new `k8s-manifest-lint` job runs `kubeconform -strict` over every manifest under `k8s/`, including Jobs.
- **K8s validation scripts:** `tests/k8s/hpc-engine-recovery-cycle.sh` and `tests/k8s/rollout-restart-under-load.sh`.
- **Docs:** `docs/kubernetes-deployment-and-pod-recovery-guide.md` — build/deploy/validate guide covering both `eop-server` and `hpc-engine` workloads (probes, restart, reconnect/re-registration behavior).
- **Merged Welcome Message (ACK):** The server now responds to a successful `REGISTER` command with a unified greeting/ACK string formatted as `ACK Server v1.0 | TIME <timestamp> | SESSION_ID <node_id>`.

### Changed
- **Shared K8s ConfigMap renamed:** `eop-server-config` → `eop-global-config`, now also carrying `hpc-engine`'s configuration (`HPC_NODE_ID`, `HPC_BUNKER_NAME`, `HPC_CAPACITY`, `OMP_NUM_THREADS`, `EOP_SERVER_HOST`).
- **Direct Node Registration:** Replaced the legacy two-step session process. The initialization of a session directly relies on parsing a `REGISTER` command from an accepted connection.
- **Node ID Decoupling:** Re-adapted the connection limit verification. Allowed connection count (`MAX_CLIENTS=10`) is exclusively checked against the global active connections tracker instead of bounding numerical ranges from `node_id`.
- **Integration Test Overhaul:** Updated the `testConnection.cpp` `Reaches100ConnectionsSuccessfully` test case to perform the 100-cycle loop (Connect → Register → Acknowledge → Disconnect) utilizing the standard unified protocol, dropping its dependency on deprecated session allocations.

### Removed
- **Legacy REQ_SESSION System:** Extracted and eliminated the legacy `isLegacySession` logic, `REQ_SESSION` command parsing, and numeric `activeSessions` indexing structures.

### Fixed
- **Docker CI (`docker-image-build`):** both `Dockerfile` and `hpc-engine/Dockerfile` now pin the `vcpkg` clone to release tag `2026.06.24` instead of the unpinned `master` HEAD. An upstream vcpkg change (`z_vcpkg_spdx.cmake`'s SPDX generation using `string(JSON ... STRING_ENCODE ...)`) required a newer CMake than the pinned `cmake>=3.30,<3.31`, breaking fresh (cache-less) builds — which is exactly what CI runs on.
- **HPC Engine heartbeat thread lifetime:** the heartbeat background thread in `hpc-engine`'s socket mode is now owned by an RAII guard (`HeartbeatGuard` in `main.cpp`). Previously a bare `std::thread`, it would call `std::terminate()` if destroyed while joinable — i.e. if an exception escaped the `ANALYZE_GRAPH` request loop, aborting the process before the socket closed or `main()`'s outer `try/catch` ran.
- **HPC Engine exception safety at the engine/socket boundary:** `processAnalyzeGraphRequest` (`engine.cpp`) now also catches non-`std::exception` throws (`catch (...)`) and serializes every response with `nlohmann::json::error_handler_t::replace`, so `dump()` itself cannot throw on invalid UTF-8 from within the error path. Closes the escape route that could trigger the heartbeat-thread crash above.
- **HPC Engine could not connect to `eop-server` inside Kubernetes:** `connectToServer()` (`main.cpp`) used `inet_pton()`, which only accepts numeric IP literals — but the K8s Deployment points `EOP_SERVER_HOST` at the Service's DNS name (`eop-server`), so the pod exhausted all retry attempts and exited every time, leaving `deployment/hpc-engine` permanently stuck below its readiness threshold. Switched to `getaddrinfo()`, which resolves both hostnames and IP literals (docker-compose/local usage with a raw IP is unaffected). Found and verified against a live minikube cluster.
- **`hpc-engine` Deployment rollout deadlock and recovery-test pod selection:** `tests/k8s/hpc-engine-recovery-cycle.sh` matched the batch Job's Pod as well as the Deployment's (`app=hpc-engine` shared by both) — added a `mode=persistent` label to disambiguate, mirroring the Job's `mode=batch`. Separately, the default `RollingUpdate` strategy briefly ran old+new Pods together, and both registering under the same static `HPC_NODE_ID` deadlocked the rollout permanently (`ERROR_DUPLICATE`, new Pod never Ready, old Pod never removed) — switched `k8s/hpc-engine-deployment.yaml` to `strategy: Recreate`.
- **`eop-server` could never let a reconnecting node's IP change:** `registerOrReconnectNode` required `ipAddress` to match the previously stored value, contradicting `ADR-018`'s own Server Logic rule (IP should be *updated* on reconnect, not compared) and blocking any Kubernetes-managed node (fresh IP on every Pod restart) from ever reconnecting while `eop-server` itself stayed up.
- **`eop-server` never detected an HPC Engine session disconnecting:** sessions reserved for dispatch (`ADR-022`) are excluded from both the heartbeat-timeout monitor and the generic poll-based read loop by design, and neither passive path was catching disconnection in practice — a node stayed registered `ONLINE` with a stale IP indefinitely after its Pod was deleted. Added a non-consuming `MSG_PEEK` liveness check for these sessions inside the existing timeout-monitor tick.
- **AC7 rollout-restart load test reported ~40 false failures:** `tests/k8s/rollout-restart-under-load.sh` used a single `kubectl port-forward` that pins to whichever Pod backs the Service at startup and never re-resolves — its tunnel died for good the moment that Pod was deleted mid-rollout, well after the Service itself had already handed traffic off cleanly to the replacement Pod (confirmed via `kubectl get endpoints -w`: no gap). Now runs port-forward under a small self-restarting supervisor and gives the load client's own REGISTER attempt a bounded retry within its existing per-operation budget, absorbing the supervisor's brief reconnect window the way a real reconnecting client would. Verified live: 0 failures across 3 consecutive runs.
