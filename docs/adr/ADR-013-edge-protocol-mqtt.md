# ADR-013: Edge Protocol Selection — MQTT over gRPC

**Status:** Accepted (v1.0, issue #66). Adapted from the PRD reference ADR-013; implemented by
US-401 (#68), US-402 (#69) and US-404 (#72).

## Context and Problem

v1.0 adds edge devices — an ESP32 running ZephyrOS in each bunker — that send telemetry to EOP
every second. The protocol between device and cluster has to fit these constraints:

* **Hardware:** ESP32, ~520 KB of SRAM and ~4 MB of flash, shared with the ZephyrOS kernel, the
  WiFi stack and the application.
* **Connectivity:** WiFi that drops; the device must survive disconnections and reconnect on its
  own (US-401 AC5, US-402).
* **Client availability:** the protocol client must exist in ZephyrOS.
* **Semantics:** periodic telemetry; the device does not wait for an answer to keep sampling, but
  telemetry must not be lost during an outage (US-402 AC4) and duplicates must be detectable
  (US-402 AC7).

The v0.1 socket protocol (ADR-001, ADR-003) and a gRPC API are the two options already familiar
to the squad. The PRD makes this choice part of the final defense: the answer to *"why not gRPC on
the ESP32?"* must be quantitative.

## Options Considered

| Constraint | gRPC (HTTP/2 + TLS) | v0.1 text protocol over TCP | **MQTT** |
|---|---|---|---|
| Memory on the device | HTTP/2 framing, HPACK and a TLS stack: ~150–300 KB baseline | Small client, but every reliability feature has to be written | Fixed 2-byte header; Zephyr's `mqtt_client` ~20–40 KB with TLS off |
| Fits next to kernel + WiFi in ~520 KB | No: kernel and WiFi stack take most of the SRAM before the application starts | Yes | Yes, with margin |
| ZephyrOS client | None in Zephyr's networking stack | Would be custom code | `mqtt_client`, a first-class Zephyr subsystem |
| Delivery guarantee | Application-level acknowledgements over streams | Application-level, to design | QoS 1 (at-least-once) with PUBACK, natively |
| Disconnected devices | Long-lived connection assumed | Session tied to one TCP connection (ADR-018) | Persistent sessions (`clean session = false`), broker keeps QoS 1 messages |
| Fan-in / decoupling | Point to point | Every device holds a socket to `eop-server` | Broker decouples devices from consumers; the ingestor subscribes with a wildcard |

## Decision

1. **Edge devices use MQTT 3.1.1 over TCP.** 3.1.1 is what both ends implement fully: Zephyr's
   `mqtt_client` and the Go client used by the edge ingestor (`paho.mqtt.golang`). MQTT 5 user
   properties would carry trace headers, but nothing in v1.0 needs them (see ADR-028).
2. **QoS 1** for telemetry, events and health. QoS 0 is rejected because US-402 forbids losing
   telemetry; QoS 2 is rejected because its four-message handshake doubles the traffic of a
   1-second stream for a guarantee the ingestor already provides by deduplication (ADR-028).
3. **Topics:** `eop/bunker/{node_id}/telemetry` (samples, US-401), `eop/bunker/{node_id}/events`
   (`RECONNECTED`, US-402 AC6) and `eop/bunker/{node_id}/health` (restart counters and dropped
   messages, US-402 AC8, US-403 AC2). The prefix `eop/bunker` is configurable on the device
   (`prj.conf`, US-401 AC7) and in the ingestor.
4. **Broker: Eclipse Mosquitto** as a Kubernetes Deployment with a PersistentVolumeClaim
   (`persistence true`), so QoS 1 messages queued for a disconnected subscriber survive a broker
   restart. One replica: Mosquitto has no clustering, and a broker restart is covered by device
   buffering (US-402) and persistent sessions.
5. **Two listeners:** `8883` with TLS for devices (server certificate from a CA generated by
   `make edge-certs`, mounted from a Secret; mbedTLS on the device, `CONFIG_EOP_MQTT_TLS`), and
   `1883` without TLS reachable only inside the cluster, for the edge ingestor. Local development
   (docker-compose, `native_sim`) uses `1883`.
6. **Payload:** one JSON object per message, with the PRD fields plus two the system needs:

   ```json
   {"node_id": "vault-101", "bunker_name": "Vault-101", "timestamp": "2026-11-02T14:03:07.120Z",
    "temperature": 21.4, "status": "OK", "message_id": 4182, "boot_id": "9f3c27a1"}
   ```

   `message_id` (monotonic per boot) and `boot_id` (random per boot) identify a message for
   deduplication (US-402 AC7, ADR-028); `bunker_name` comes from `prj.conf` so the device shows up
   in `/v1/nodes` with a readable name. The full contract is in
   `docs/edge-telemetry-protocol-v1.0.md`.

### Implementation notes: no ESP32 board

The squad has no ESP32 board. The firmware is built for Zephyr's `native_sim` board, where it
runs as a Linux process and uses the host's sockets (Native Simulator offloaded sockets), so the
MQTT traffic, the broker and everything downstream are real. The same source builds for
`esp32_devkitc`; a board can be flashed later without code changes. What the simulation does and
does not prove is listed in ADR-014.

## Consequences

* **Positive:** the device needs only a small, native client; delivery and reconnection semantics
  come from the protocol; devices never connect to `eop-server` directly, so thousands of devices
  do not mean thousands of sessions in the C++ server.
* **Negative:** two new components (broker, ingestor) to deploy, observe and include in the
  product (US-406). At-least-once delivery means duplicates by design; they are removed in the
  ingestor (ADR-028). The broker is a single replica; its restart is an outage for devices,
  absorbed by their offline buffer.
* **Defense answer:** gRPC needs ~150–300 KB for HTTP/2 + TLS before any application code, on a
  device with ~520 KB of SRAM already shared by the kernel and the WiFi stack, and Zephyr has no
  gRPC client. MQTT needs ~20–40 KB, is a native Zephyr subsystem, and its QoS 1 and persistent
  sessions are exactly the delivery model telemetry over unreliable WiFi needs.
