# EOP v0.2 — Known Limitations at Release Time

This document lists the acceptance criteria and NFRs from the PRD that were measured and did
**not** pass, or could not be measured at all, as of the v0.2 close-out. Every other AC across
US-201 through US-206 is either implemented and verified, or tracked to closure in the linked
issues/PRs. This is not a list of missing features — it is the honest result of running the
acceptance tests for real, with the evidence and root cause for each entry so the course staff can
evaluate the trade-off rather than take a claim on faith.

Full raw evidence (logs, `.csv` machine-health traces from `tests/evidence/watchdog.py`,
generated graphs) is in `~/Documentos/Facultad/SO2/evidencia-v0.2/` (outside the repo, since it is
run-local scratch data, not source). Everything cited below is reproducible with the commands
given in each section.

## 1. US-202 AC2 — speedup ≥ 2× with 4 threads on graphs ≥ 50,000 nodes

**Status: not met at 100,000 nodes.**

`hpc-engine/benchmarks/BENCHMARK_REPORT.md` (generated by `make benchmark`, see there for the
full matrix and Amdahl analysis) measures, on this machine (Intel i7-8550U, 4 physical cores):

```
Nodes      Threads   Median time   Speedup
50,000     4         1.322 s       2.86×   (meets the AC on its own)
100,000    2         6.125 s       1.61×
100,000    4         7.998 s       1.23×   <- worse than 2 threads
100,000    8 (HT)     12.3 s       0.80×   <- worse than 1 thread
```

The criterion names "≥ 50,000 nodes" as a floor, not a single point, so it is evaluated across
every qualifying size measured — the worst one governs. 50,000 nodes clears the bar on its own
(2.86×); 100,000 does not (1.23×), which is what determines the ❌ above. Full data,
including 1/2/8-thread rows and the Amdahl fit, is in `hpc-engine/benchmarks/BENCHMARK_REPORT.md`
as of this branch (generated `2026-09-22`, real `make benchmark` run, `Release` build).

The pattern is consistent with a **memory bandwidth ceiling**, not a coding defect:

- Adding threads *beyond the physical core count* (8 threads on 4 cores, i.e. hyperthreading)
  measures *slower* than 4 threads at every graph size ≥ 50,000 nodes in this benchmark — a
  serial-fraction bottleneck (Amdahl) can only cap the gain from more threads, never reverse it.
  Two hardware threads on the same physical core contend for the same L1/L2 cache and the same
  memory-bandwidth budget, which a compute-bound graph traversal saturates.
- `hpc-engine/src/centrality.cpp`'s CSR adjacency plus per-thread predecessor buffers were already
  reworked for cache locality as part of ADR-024 (1.4x faster at 10,000 nodes with bit-identical
  results), which is why 50,000 nodes clears the 2× bar while 100,000 does not: the working set at
  100,000 nodes no longer fits the 8 MiB L3 cache this CPU has, regardless of thread count.

This is a genuine algorithmic/hardware limit on this class of machine, not something a
configuration change fixes. Revisiting it further would mean restructuring the graph traversal to
reduce the per-source working set (e.g. tiling / blocking the CSR scan), which is out of scope for
this close-out.

**Reproduce:** `make benchmark` (needs `VCPKG_ROOT` pointed at vcpkg pinned to `2026.06.24`,
see `hpc-engine/benchmarks/run_benchmark.sh`'s own guard for the exact tag).

## 2. US-202 AC3 — speedup ≥ 3× with 8 threads on graphs ≥ 100,000 nodes

**Status: not measurable on available hardware.**

The AC requires measuring speedup with **8 threads**, which only measures what the criterion asks
for when those 8 threads map to 8 *physical* cores. Every machine used for this project's
development and testing has 4 physical cores:

```
$ lscpu | grep -E "^CPU\(s\)|Core\(s\) per socket|Socket\(s\)|Thread\(s\) per core"
CPU(s):                4
Core(s) per socket:    4
Socket(s):             1
Thread(s) per core:    2
```

8 "CPUs" as reported by `nproc`/`lscpu`'s `CPU(s)` line are 4 physical cores × 2 hardware threads
(hyperthreading) — not 8 independent cores. Running with `OMP_NUM_THREADS=8` on this hardware
measures contention between hyperthread pairs, not the speedup from 8 independent execution
units, so any number produced here would misrepresent what the AC is asking about.
`hpc-engine/benchmarks/benchmark_report.py` detects this and reports the criterion as **not
measurable** rather than emitting a number that looks like a real measurement — see its
`physical_thread_counts()`/`speedup_verdict()` and the "no medible" row in
`BENCHMARK_REPORT.md`, instead of forcing a fail or a misleading pass.

What can be said from the data actually measured (2 and 4 physical threads, least-squares fit to
Amdahl's law in the Benchmark Report): at 100,000 nodes the fitted serial fraction is s=0.592,
predicting S(8 physical cores)=1.56× — well under the 3× target — and even the theoretical ceiling
as physical core count grows without bound is only 1/s ≈ 1.69×. This is a curve fit extrapolated
from 2 measured points, not a measurement at 8 physical cores, and should be read as a prediction,
not a result: the fit's own conclusion is that the workload is memory-bound rather than
compute-bound at that size (see §1's cache-capacity argument), which is exactly the kind of
ceiling more physical cores do not lift. The expectation, not the demonstrated fact, is that this
AC would remain difficult to clear even on real 8-core hardware.

**What would resolve this:** running the identical `make benchmark` command on a machine with 8
physical cores (not 8 threads/4 cores). No code or configuration change is needed for that —
the benchmark harness already reports physical core count and self-adjusts what it claims to
measure.

## 3. NFR — MTTR on pod crash < 200 ms

**Status: not met; no panel exists for it either.**

Measured with `tests/k8s/pod-recovery-cycle.sh` against a live minikube cluster: `kubectl delete
pod` on `eop-server` to the replacement pod reaching `Ready` took **~24 seconds**, itself above
the script's own `RECOVERY_TIMEOUT_SECONDS` default of 10s, and roughly two orders of magnitude
above the 200 ms NFR.

This is expected given how the NFR is currently implemented, not a bug: recreating a Kubernetes
pod from scratch (scheduling, image pull if not cached, container start, the app's own startup
sequence, then the readiness probe's own polling interval before Kubernetes marks it Ready) is
fundamentally a multi-second operation. 200 ms is not achievable by *recreating* a failed
instance — it is only achievable as the failover time to a **different, already-running,
already-healthy replica** taking over the failed one's traffic.

Two things block that path today, both structural:

- `k8s/deployment.yaml` (`eop-server`) runs a single replica. `eop-server` keeps its node
  registry in server-process memory (no shared/external store), so a second replica would not
  see the first's registered nodes — scaling to N replicas needs a shared state layer first
  (e.g. externalizing the registry to Redis or similar), which is a real architecture change, not
  a manifest tweak.
- There is no Grafana panel or Prometheus recording rule computing pod-death-to-ready time at
  all today; `monitoring/grafana/dashboards/` has no MTTR panel to point at even if the number
  were good.

Both are legitimate scope for a future milestone (the PRD's own NFR table lists this as enforced
"v0.2 →", i.e. an ongoing requirement, not a one-time v0.2 gate) rather than something this
close-out can safely improve without touching state management the rest of the v0.2 surface
depends on.

**Reproduce:** `EOP_K8S_DEPLOYMENT=eop-server bash tests/k8s/pod-recovery-cycle.sh` against a
running minikube cluster with `k8s/` applied.

## Everything else in US-201–US-206

Not covered above because it passes: correctness (US-201 AC1/AC2/AC4–AC8), the AC3 latency budget
itself (met **exactly**, no approximation, per ADR-024 option D — see there for the full
measurement), OpenMP correctness under ThreadSanitizer (US-202 AC4, 160/160 with zero data
races), the Benchmark Report deliverable and its Amdahl analysis (US-202 AC5), the
"when not to parallelize" finding (US-202 AC6, ~100 nodes on this hardware), `make benchmark`
itself running end to end with no manual steps (US-202 AC7), CPU usage staying within
`OMP_NUM_THREADS` (US-202 AC8), the full v0.1 integration (US-203), Kubernetes workload
management (US-204), the SLO dashboard and error-budget alerting (US-205), and the HPC
performance panel (US-206).
